## Requested Codex status behavior

The user chose **all running chats together**, not just the frontmost chat.

| State | Desired presentation |
|---|---|
| Working/thinking | Entire glass blue; large eyes/pupils look upward; rising reflections |
| Needs approval/decision | Entire glass yellow; attentive expression and gentle rim pulse |
| Terminal failure | Entire glass red; worried brows/mouth |
| Confirmed turn completion | Entire glass green; relaxed smile |
| Hover over green | Acknowledge completion and restore normal glass |
| No status established/disconnected | Neutral/sleepy appearance |

Waiting outranks working. One completed chat cannot turn the whole pet green while another observed chat is still active. After active work ends, failure outranks success. A new work cycle clears older terminal colors. Hover must not dismiss blue/yellow/red.

**Continuity requirement:** blue/yellow remain until a replacement status arrives. Generic Stop, SessionEnd and quiet time are not proof of completion. The user explicitly rejected a neutral gap between blue and green. v1.8.1 removes the earlier five-minute expiry.

**Semantic limit:** current green proves a stored Codex **turn** completed, not that a whole multi-turn goal succeeded. Yellow is a detected request signal; another hook can auto-resolve approval. Async input has no dedicated answer-resolution hook in this implementation, so pending yellow clears on new user input or turn outcome.

## How terminal status is currently read

CodexTurnMonitor starts the installed desktop CLI as a local stdio app-server. Hardcoded candidates currently are:

```text
/Applications/ChatGPT.app/Contents/Resources/codex-cli/bin/codex
/Applications/Codex.app/Contents/Resources/codex
```

Only initialize/initialized and this read-only query are sent:

```json
{"method":"thread/turns/list","params":{"threadId":"KNOWN_SESSION_ID","limit":1,"sortDirection":"desc","itemsView":"notLoaded"}}
```

- Poll every2s after initialization. Track known hook turn IDs and require exact returned turn-ID equality.
- Only completed/failed/interrupted become terminal events. inProgress, absent/mismatched results or protocol errors do not manufacture an outcome.
- Reject item-bearing responses; do not retain error text or message contents.
- Queries stop after43,200 attempts per observed turn (nominally24h). There is no state-expiry fallback, so unmatched/missing outcomes can leave active color latched.
- Hook session_id is **not universally guaranteed to equal stored threadId**, especially across session/subagent/fork variants. This needs diagnosis, not relaxed ID matching.
- A separate server reads stored metadata; it does not prove another host's live approval state.
- Earlier research found no documented default desktop control socket. Private IPC registration could broadcast full snapshots; it was deliberately not used. `thread/read` can contain prompt preview even with turns omitted, so it was not used either.

Previously consulted official references; recheck installed-version behavior before changes:

- https://learn.chatgpt.com/docs/hooks
- https://learn.chatgpt.com/docs/app-server
- https://learn.chatgpt.com/docs/config-file/config-advanced#notifications

Do not use PostModelRequest attempt failure as terminal failure: retries happen within a turn. A generic Stop also does not establish successful completion.
